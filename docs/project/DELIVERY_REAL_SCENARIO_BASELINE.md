# 独立交付：贴近真实计算场景的 hipANS → LDS baseline

2026-10-11 制定；对应战略 S0 / S1。当前仅完成计划，尚未启动本交付实验。
执行状态使用同一 R0–R3 编号，见 [STATUS.md](STATUS.md)。

## 目标

在真实模型权重及其目标矩阵计算需求下，建立可验证的未优化 hipANS → LDS
基线并解释瓶颈，为后续优化及 ANS+GEMM 融合提供依据。论文的融合计算场景
作为参照，不把重复小矩阵获得的资源饱和速率作为主要性能目标。

## 工作负载提案

首选沿用上游 entropyflow-lab 的 DeepSeek-V4-Flash-Base，筛选原生 FP8 的较大
真实投影矩阵；若其格式或实际计算用途不适合，则考察上游 GLM-5.2-FP8 的
投影或专家矩阵。理由是保留上游压缩性分析的对应关系、避免新增量化变量，
并让形状与权重分布来自真实模型，而不是放大、拼接或复制现有权重。
两者目前是候选，不声称已确认具体 tensor、尺寸或计算适配性。

R0 需提供 1–2 个经实际模型配置和 tensor 元数据核实的候选及选择理由，
明确推理阶段、输入规模、矩阵角色和权重需求，经用户确认后才提取新权重。
选择更大矩阵必须有场景依据；并非矩阵越大越真实。现有 8 MiB 专家矩阵
保留作工程验证，不要求将论文六个模型全部纳入或跨越某个缓存容量。

优先原生 FP8，本轮不使用 4-bit。BF16 如需进入本交付，须先明确可逆表示及
验证口径，不将 BF16 转 FP8 的量化结果声称为原 BF16 的无损恢复。

## 交付节点

| 编号 | 任务描述 | 成功标准 |
|---|---|---|
| R0 | 确认代表性真实权重与计算场景 | 模型、矩阵、格式及推理用途可追溯；权重读取和复用需求有依据；候选经用户确认 |
| R1 | 建立场景对应的离线权重包及正确性证据 | 压缩权重和元数据可重复使用；按目标需求恢复到 LDS 后逐位正确；真实权重与重复消费量分别清楚 |
| R2 | 建立两类 AMD 机器的场景解码 baseline | 使用实际未优化 hipANS；同一场景分别测量 MI350X / MI300X；结果可复查，明确未融合计算的局限 |
| R3 | 交付瓶颈证据与后续优化建议 | 性能限制有对应场景的 profiling 证据；未知或不可用证据显式记录；下一优化交付及融合条件明确 |

依赖顺序为 R0 → R1 → R2 → R3。R0 确认负载、R1 正确性验收、R2 基线返回
及 R3 归因完成分别形成阶段性反馈，不一次性把后续优化和融合包含进来。
MI350X 优先获得反馈，MI300X 独立记录，不互用硬件上限或调优结论。

## 场景与验收边界

- 模型权重提前压缩并准备元数据；解码热路径从设备端压缩权重恢复到 LDS，
  不将在线编码或完整权重的全局解压输出混入目标路径。
- 目标 GEMM 的权重消费粒度、访问顺序及复用决定解码需求。不能默认一次
  推理只解码矩阵一次，也不能把 batch 或 token 数简单换成完整矩阵副本数。
- 论文的融合 GEMM 评估与本交付的解码阶段代理实验分开描述。后者即使按
  目标需求输出后丢弃，也缺少消费者的计算、争用和流水线反馈，不能声称
  已测得融合或端到端收益；不能验证的场景假设必须明示。
- 区分唯一权重规模、实际驻留工作集与实际解码产出。有效输出吞吐以实际
  必需且完成的产出计数，同时报告对应完成时间，不以副本乘法虚构实际工作。
- 正式 baseline 的访问与缓存条件可追溯；重复测量、资源供给及缓存压力实验
  可辅助诊断，但 replicas 饱和或人为冷缓存条件不替代主要场景验收。
- 未定义分子分母的“论文 30%”不是验收目标。报告解码输出速率及实际资源
  证据，不把输出 bytes/s 除以 HBM 参考值解释为 LDS 硬件利用率。
- 本交付不自动实施解码算法优化或 GEMM 融合；允许后续修改 hipANS 的权限
  保留。entropyflow-lab 及其现有数据只读。

工程配置、命令、作业与具体测量记录放在 STATUS 和实验报告中，不写入此战略计划。
